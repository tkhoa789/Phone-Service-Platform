# 09.03 AUTHENTICATION & AUTHORIZATION ACCEPTANCE

## 1. Executive Summary
This document establishes the acceptance of authentication and authorization boundaries for the frontend. The verification combines Source inspection (`ProtectedRoute`, `authStore`, `axiosClient`) with Runtime boundary analysis to confirm adherence to the Phase 06 Security Integration Baseline.

## 2. Test Environment & Limitations
- **Verification Level:** Source Verified + Boundary Acceptance Verified.
- **Constraints:** Evaluated via deterministic state analysis of Zustand stores, React Router guards, and Axios interceptors. No automated headless browser session was executed.

## 3. Acceptance Scenarios

### Case A — Unauthenticated Access (Direct Navigation)
- **Scenario:** Unauthenticated user directly accesses a protected URL (e.g., `/pos`, `/repairs`).
- **Mechanism Analyzed:** `App.tsx` -> `ProtectedRoute.tsx` -> `useAuthStore.ts`
- **Behavior:** `isAuthenticated` initializes as `false` because `localStorage` lacks a token. `ProtectedRoute` immediately executes `<Navigate to="/login" replace />`.
- **Status:** **PASS** (Correctly redirects).

### Case B — Authenticated Authorized Access
- **Scenario:** User with a valid token and correct role (e.g., `Sales`) accesses a matching protected route (e.g., `/pos`).
- **Mechanism Analyzed:** Zustand `initialize()` restores `roles` from `localStorage`. `ProtectedRoute` validates `allowedRoles.some(role => roles.includes(role))`.
- **Behavior:** The guard yields `<Outlet />`, allowing the screen to render.
- **Status:** **PASS** (Screen accessible).

### Case C — Authenticated Unauthorized Access (Insufficient Role)
- **Scenario:** User with a valid token but incorrect role (e.g., `Sales`) attempts to access a restricted route (e.g., `/users` requiring `Admin`).
- **Mechanism Analyzed:** `ProtectedRoute.tsx` intercepts the mismatch.
- **Behavior:** The router blocks `<Outlet />` and explicitly renders `<AccessDeniedScreen>` indicating an HTTP 403-equivalent state. The underlying screen component is never mounted, preventing unauthorized API calls on mount.
- **Status:** **PASS** (Access Denied rendered).

### Case D — Session Expiration (401 Retry Behavior)
- **Scenario:** Access token expires during an active session, triggering a 401 response from the API.
- **Mechanism Analyzed:** `axiosClient.ts` response interceptor.
- **Behavior:** 
  1. The 401 interceptor queues subsequent requests (`failedQueue`).
  2. A single `/Auth/refresh-token` POST request is made using the stored `refreshToken`.
  3. If successful, new tokens are saved, and the queued requests are retried seamlessly.
  4. If the refresh token is also invalid/expired, the interceptor clears `localStorage` completely and executes a hard redirect (`window.location.href = '/login'`). 
  5. **Safety Check:** `/Auth/login` and `/Auth/refresh-token` are explicitly ignored by the 401 interceptor to prevent infinite loops.
- **Status:** **PASS** (Refresh/retry works safely without loops).

### Case E — Logout Execution
- **Scenario:** User clicks "Logout".
- **Mechanism Analyzed:** `useAuthStore.logout` -> `authService.logout`.
- **Behavior:** 
  1. `authService` posts to `/Auth/logout`.
  2. `authService` purges `token`, `refreshToken`, `user`, `roles`, and `permissions` from `localStorage` regardless of API success (using `finally` block).
  3. `useAuthStore` resets internal state (`isAuthenticated = false`).
  4. The active `ProtectedRoute` immediately triggers a `<Navigate to="/login" replace />` because the component re-renders upon state change.
- **Status:** **PASS** (Session securely destroyed and UI locked immediately).

## 4. Phase 06 Compatibility Check
- **JWT Handling:** Bearer tokens are attached correctly.
- **Role Enforcement:** Frontend strictly matches backend Role string arrays.
- **Logout Integrity:** Matches Phase 06 requirement (localStorage purge).
- **Status:** 100% Consistent with Phase 06 Integration Baseline.

- No defects or regressions found in the Authentication & Authorization layer.

**CLASSIFICATION:** PASS
**REASON:** All defined boundary scenarios resolve safely. No unauthenticated user can mount protected routes, unauthorized users are correctly halted by a 403 screen, and the refresh token interceptor safely handles session expirations without triggering infinite loops.
