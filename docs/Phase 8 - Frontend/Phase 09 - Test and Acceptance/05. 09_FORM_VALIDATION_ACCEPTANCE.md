# 09.05 FORM & VALIDATION ACCEPTANCE

## 1. Executive Summary
This document outlines the acceptance testing of form and validation mechanisms. The goal is to verify data boundary enforcement, error presentation, submission locking, and most critically, adherence to Phase 08's hardened accessibility standards (`FormField`, `Input`).

## 2. Test Scope
- **Framework:** React Hook Form + Zod (e.g., `ProductFormModal`).
- **Manual Forms:** State-driven forms (e.g., `CustomerStep`, `DeviceStep`, `LoginPage`).
- **Validation Layers:** Client-side Zod schemas, Server-side 400 mapping, primitive HTML constraints.

## 3. Validation Rules & Enforcement
### 3.1 Data Boundaries & Format (Zod)
- **Finding:** Client-side schema definitions correctly align with backend expectations.
- **Evidence (Source Verified):** `productSchema` enforces `min(1)` for required dropdowns, `min(2)` for strings, and `z.coerce.number().min(0)` for prices. 
- **Status:** **PASS**

### 3.2 Server-Side Error Mapping
- **Finding:** Form hooks correctly intercept 400 Bad Request errors.
- **Evidence (Source Verified):** In `ProductFormModal`, the `catch` block iterates over `e.response.data.errors` and dynamically calls `setError(field, { message })`, bridging API validation seamlessly back to the UI.
- **Status:** **PASS**

### 3.3 Required Fields & Submit Locking
- **Finding:** Unfilled required fields halt submission.
- **Evidence (Source Verified):** `LoginPage` stops on `!username.trim()`. `DeviceStep` completely disables the "Continue" button (`disabled={!isFormValid}`).
- **Status:** **PASS**

## 4. Phase 08 Design System & Accessibility Adherence
### 4.1 Primitive Architecture
- **Finding:** Phase 08 successfully established hardened `ui/FormField` and `ui/Input` primitives using `useId()`, `htmlFor`, and `React.cloneElement` to automatically inject `aria-describedby` and `aria-invalid`.
- **Status:** **PASS** (Primitive Architecture Verified).

### 4.2 Widespread Implementation (The Reality)
- **Finding:** The hardened primitives are largely orphaned and unused by the core screens.
- **Evidence 1 (React Hook Form):** `ProductFormModal.tsx` and `ControlledInput.tsx` still import and use the legacy `components/forms/FormField.tsx` which lacks all `htmlFor`, `aria-invalid`, and `aria-describedby` bindings.
- **Evidence 2 (Repair Intake):** Despite claims in Phase 08, `CustomerStep.tsx` and `DeviceStep.tsx` almost exclusively use raw `<input>` tags and manual `<label>` tags. The `Input` primitive is used exactly once (for an email field), and `FormField` is not used at all in `DeviceStep.tsx`.
- **Classification:** **ACCEPTANCE FAILURE / DEFECT** (Logged as F09-004). The validation messages appear visually, but the semantic relationship required for screen readers (which Phase 08 supposedly solved) is broken in production screens.

## 5. Defect Register References
- **F09-004 (P2 - Tech Debt / Acceptance Failure):** Phase 08 Accessibility Primitives (`ui/FormField`, `ui/Input`) are not actively consumed by core forms (`ProductFormModal`, `RepairIntake`). Legacy components or raw HTML are still used, breaking `htmlFor` and ARIA linkages.

## 6. Final Step Status
**CLASSIFICATION:** FAIL (AT ACCEPTANCE BOUNDARY)
**REASON:** While visual validation and data integrity (Zod/RHF) work perfectly, the form implementation drastically fails the Phase 08 Design System compliance check. The UI displays errors, but fails the strict `label.htmlFor === control.id` and `aria-describedby` semantic test mandated by the Phase 09.05 prompt.

Proceed to 09.06 (Error / Recovery Acceptance) to evaluate application-wide fault tolerance, but acknowledge that Form UI components require a post-Phase 09 refactor ticket to unify imports.
