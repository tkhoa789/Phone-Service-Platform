# 09.04 UI STATE ACCEPTANCE

## 1. Executive Summary
This document records the evaluation of UI state transitions across the application, answering whether the frontend gracefully manages the lifecycle of data interactions (Loading, Empty, Submitting, Error) without breaking or allowing duplicate submissions. 

## 2. Test Environment & Limitations
- **Verification Level:** Source Verified (Analysis of React component hooks, state variables, and conditional rendering).
- **Scope Analyzed:** Key P0/P1 components (`ProductListPage`, `RepairListPage`, `PosPaymentModal`, `CustomerStep`).

## 3. UI State Lifecycle Acceptance

### 3.1 Initial & Loading States
- **Finding:** Correctly implemented.
- **Evidence:** `ProductListPage.tsx` utilizes `isLoading && !allProducts.length` from React Query to render a `<PageSkeleton />` on initial mount. For subsequent fetches (e.g., pagination), it renders an inline table row indicating loading (`<td colSpan={5}>...loading...</td>`). `RepairListPage` uses manual `loading` state to achieve the exact same inline table fallback.
- **Status:** **PASS** (Source Verified)

### 3.2 Empty States
- **Finding:** Correctly implemented.
- **Evidence:** After loading completes, arrays are checked (`paginatedProducts.length === 0`). If true, a dedicated fallback row is shown (e.g., "Chưa có dữ liệu" / `tProd.emptyProducts`).
- **Status:** **PASS** (Source Verified)

### 3.3 Submitting & Disabled States (Duplicate Submission Protection)
- **Finding:** Action-locking is robustly implemented.
- **Evidence (Modal):** `PosPaymentModal` utilizes an `isSubmitting` boolean bounded by `try...finally`. This state is passed to the primitive `<Button loading={isSubmitting}>`, which disables interaction and displays a spinner.
- **Evidence (Validation Logic):** `<Button disabled={cart.length === 0}>` correctly locks progress when preconditions aren't met.
- **Status:** **PASS** (Source Verified)

### 3.4 Error & Recovery States (Data Fetching)
- **Finding:** Global coverage exists, but local component coverage is missing.
- **Evidence:** When `useProducts` or `serviceService.getRepairs()` fails, the UI relies completely on the global `toast.error` (from `axiosClient` or manual catch blocks) to alert the user. However, the internal list component does not explicitly check `isError` to render an inline "Failed to load" message with a Retry button; it silently defaults to rendering the "Empty State". 
- **Classification:** **TEST GAP / OBSERVATION** (Logged as F09-002). The system does not crash, but the UX conflates "No data exists" with "Failed to fetch data".

### 3.5 Jarring State Transitions
- **Finding:** Some local loading states unmount the working context completely.
- **Evidence:** In `CustomerStep.tsx` (Repair Intake), setting `loading = true` during customer creation hides the entire `<form>` and replaces it with a div saying "Loading...". This guarantees no duplicate submission, but is visually jarring compared to a localized button spinner.
- **Classification:** **OBSERVATION** (Logged as F09-003).

## 4. Defect Register References
- **F09-002 (P3 - UX GAP):** Lack of explicit inline Error/Retry states for data grids.
- **F09-003 (P3 - UX GAP):** `CustomerStep.tsx` form completely unmounts during submission loading.

## 5. Final Step Status
**CLASSIFICATION:** PASS WITH OBSERVATIONS
**REASON:** The core UI states (Loading, Empty, Submitting) function safely and prevent catastrophic failures (e.g., no double-submit race conditions). The application avoids crashing on state changes. The identified gaps (F09-002, F09-003) are purely UX enhancements and do not constitute blocking Functional Defects.
