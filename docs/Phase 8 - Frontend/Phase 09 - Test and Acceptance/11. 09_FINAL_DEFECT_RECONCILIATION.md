### 3.1 FIX PLAN FOR F09-006: Warranty API Signature Mismatch
- **Category:** Functional Blocker (Data corruption / 400 Bad Request).
- **Affected Workflow:** Warranty Swap (Replacement Device).
- **Root Cause Trace:**
  - **UI Event:** User clicks "XÃ¡c nháº­n Ä‘á»•i mÃ¡y" in `WarrantyReplacementModal.tsx`.
  - **Frontend Service (`serviceService.ts`):** `updateWarrantyStatus` defines positional arguments `(id, status, rowVersion, replacementImei)`.
  - **Payload Construction:** The service maps this into a JSON body `{ warrantyTicketId: id, status, replacementImei, rowVersion }`.
  - **API Contract (`UpdateWarrantyStatusCommand.cs`):** Expects `{ WarrantyTicketId, Status (enum), Action (string), Description, NewImei, RowVersion (byte[]) }`.
  - **Discrepancy:** The modal passes `rowVersion` (base64 string) into the `status` argument, and the word `'Completed'` into the `rowVersion` argument. Furthermore, the frontend service names the IMEI variable `replacementImei` instead of `newImei`, and completely omits the required `Action` field.
- **Actionable Fix (Bounded):**
  1. Modify `serviceService.ts` -> `updateWarrantyStatus` signature to match the backend C# record: `(id: string, status: string, action: string, description: string | null, newImei: string | null, rowVersion: string)`.
  2. Map the payload strictly to `{ warrantyTicketId: id, status, action, description, newImei, rowVersion }`.
  3. Modify `WarrantyReplacementModal.tsx` to call the service with the correct positional arguments: `(warrantyTicketId, 'Completed', 'Swap', null, replacementImei, rowVersion)`.
- **Regression Scope:** Extremely narrow. Only affects `WarrantyReplacementModal` and `WarrantyListPage` status transitions.

### 3.2 FIX PLAN FOR F09-005: Missing Repair Processing Workflow
- **Category:** Missing Core Feature / Workflow Breakage.
- **Affected Workflow:** Repair Technician Execution (Assign Tech -> Repairing -> Add Parts -> Calc Cost -> Complete).
- **Root Cause Trace:**
  - The API contains endpoints for adding parts (`POST /api/RepairTicket/part` which is incorrectly mapped in the backend as `[HttpPost("{id}/parts")]` while the frontend sends to `/part`).
  - The UI (`RepairListPage.tsx`) contains status toggle buttons but entirely lacks a UI trigger to open the `AddRepairPartModal.tsx`.
  - The component `AddRepairPartModal.tsx` is completely orphaned.
- **Actionable Fix (Bounded):**
  1. **Fix API Signature:** Correct the `serviceService.ts` -> `addRepairPart` endpoint path to match the backend (or fix the backend route to match frontend convention, whichever is simpler without breaking backend contracts. Easiest: change frontend Axios call to `axiosClient.post('/RepairTicket/${command.repairTicketId}/parts', command)`).
  2. **Integrate UI:** In `RepairListPage.tsx`, add an "Add Parts" action button to the repair ticket row (visible when status is `Repairing`).
  3. **Connect State:** Wire the new button to mount `<AddRepairPartModal repairTicketId={selectedTicket.id} />`. 
  4. Ensure `AddRepairPartModal` calls `loadRepairs()` on success so the updated total cost is reflected.
- **Regression Scope:** Medium. Affects `RepairListPage.tsx` UI rendering and hooks into existing `AddRepairPartModal`. Does not alter POS or Warranty workflows.
