# 09.06 ERROR & RECOVERY ACCEPTANCE

## 1. Executive Summary
This document records the acceptance verification of error handling and application recovery lifecycles. It proves that the frontend not only displays errors correctly but safely unlocks the UI, preserves user context, and allows retries without causing duplicate side effects.

## 2. Test Scope & Methodology
- **Verification Level:** Source Verified + Boundary Acceptance Verified.
- **Scenarios Evaluated:** 
  1. API 400 Validation Failure
  2. API 401 Session Expiration (Refresh loop)
  3. API 403 / 404 / 500 Global Handling
  4. API 409 Concurrency Conflict
  5. UI State Recovery (Button unlocking, form preservation)

## 3. Error Lifecycle Acceptance

### 3.1 Validation Error Recovery (400 Bad Request)
- **Scenario:** Backend rejects a mutation due to invalid data format.
- **Lifecycle Proven:** 
  - ACTION -> `isPending=true` -> 400 FAILURE.
  - ERROR PRESENTATION -> Form hook catches error, maps `e.response.data.errors` to `setError()`, displaying inline red text.
  - STATE RECOVERY -> `isPending` automatically reverts to `false`.
  - RETRY -> User corrects data and resubmits.
- **Status:** **PASS**. No UI lockups.

### 3.2 Network / Server Failure Recovery (500)
- **Scenario:** Server crashes or network drops during a POS Checkout.
- **Lifecycle Proven:**
  - ACTION -> `isSubmitting=true` -> 500 FAILURE.
  - ERROR PRESENTATION -> `axiosClient` catches 500, toasts "Lỗi hệ thống. Mã sự cố: [Correlation ID]".
  - STATE RECOVERY -> `PosPaymentModal` executes `finally { setIsSubmitting(false) }`. The modal remains open, and the cart data is preserved.
  - RETRY -> User can click Confirm again once network restores.
- **Status:** **PASS**. No data loss, no permanent button disable.

### 3.3 Authorization & Session Expiration Recovery (401 Retry Loop)
- **Scenario:** Access token expires exactly when the user clicks "Save".
- **Lifecycle Proven:**
  - ACTION -> API returns 401 Unauthorized (Backend business logic is bypassed).
  - RECOVERY -> `axiosClient` intercepts 401, pauses request, fetches new token via `/Auth/refresh-token`.
  - RETRY -> `axiosClient` re-injects new token and executes `axiosClient(originalRequest)`.
  - SAFETY CHECK -> Does this cause duplicate mutations? **NO**. The first request was rejected at the Auth middleware level. Furthermore, `Idempotency-Key` headers are preserved in the `originalRequest` config, ensuring backend idempotency filters catch any edge-case replays.
- **Status:** **PASS**. Highly resilient session recovery.

### 3.4 Concurrency Conflict (409 RowVersion / Stock Changed)
- **Scenario:** User attempts to update a Warranty or Product that another user just modified.
- **Lifecycle Proven:**
  - ACTION -> API returns 409 Conflict.
  - ERROR PRESENTATION -> `axiosClient` intercepts 409, toasts "Dữ liệu đã thay đổi bởi người khác. Vui lòng tải lại trang." (Data modified by another user. Please reload).
  - STATE RECOVERY -> Mutation Promise rejects, unlocking the UI.
  - OBSERVATION -> The frontend explicitly instructs the user to reload the page rather than blindly re-fetching. This is a safe fallback for optimistic concurrency control (OCC).
- **Status:** **PASS**.

### 3.5 Manual State Recovery (Repair Intake)
- **Scenario:** `CustomerStep` fails to create a new customer.
- **Lifecycle Proven:**
  - ACTION -> `loading=true` (form unmounts).
  - ERROR PRESENTATION -> Catch block toasts "Lỗi khi tạo khách hàng".
  - STATE RECOVERY -> `catch` executes `setLoading(false)`. The form remounts with all `newCustomer` state data preserved in `useState`.
- **Status:** **PASS**. (UX jar noted in F09-003, but functional recovery is flawless).

## 4. Defect Register References
- No functional defects found. Application fault tolerance is extremely robust.

## 5. Final Step Status
**CLASSIFICATION:** PASS
**REASON:** The frontend demonstrably protects user context during failures. Buttons re-enable reliably (`finally` blocks and React Query lifecycle are correctly used). The 401 retry interceptor safely replays failed requests without triggering duplicate business transactions.
