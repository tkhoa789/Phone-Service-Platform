# 09.01 TEST STRATEGY & SCOPE

## 1. OBJECTIVE
The core objective of Phase 09 is to answer a single question:
**Does the frontend actually work correctly for the intended business workflows?**

Phase 09 verifies that the frontend:
- Renders correct screens and routes (Phase 04 baseline).
- Operates strictly within defined UI states and interactions (Phase 05 baseline).
- Integrates accurately with the hardened API contracts (Phase 06 baseline).
- Maintains functionality without regression following UI standardization (Phase 08 baseline).
- Handles edge cases safely (errors, network failures, unauthorized access).

## 2. GOVERNANCE RULE: THE ACCEPTANCE TRIANGLE
**BUILD PASS ≠ TEST PASS ≠ ACCEPTANCE PASS**
- **BUILD PASS**: The application compiles successfully. (Verified via `npm run build`).
- **TEST PASS**: The technical layers communicate without unhandled exceptions (HTTP 200).
- **ACCEPTANCE PASS**: The end-user can successfully complete the intended business task from start to finish. Phase 09 is strictly evaluated on Acceptance Pass.

## 3. EVIDENCE LEVELS
1. **Level 1 — SOURCE VERIFIED**: Inspecting code to ensure routes, components, and handlers exist. (Insufficient for Phase 09 approval).
2. **Level 2 — RUNTIME VERIFIED**: Executing the application to confirm UI actions trigger state changes and HTTP requests correctly.
3. **Level 3 — ACCEPTANCE VERIFIED**: End-to-end confirmation that business workflows yield the correct business outcomes (e.g., POS Order Completed, Repair Ticket Assigned).

## 4. IN-SCOPE (Risk-Based Acceptance)
Testing prioritizes critical business workflows over exhaustive checkbox testing.

**P0 — Business Critical**
- POS (Cart, Vouchers, Payment, Order Creation)
- Repair (Intake, Technician Assignment, Parts, Status, Payment)
- Authentication & Authorization Guards
- Warranty (RowVersion conflict handling)

**P1 — Core Operations**
- Customer Management
- Inventory & Products
- Service Appointments

**P2 — Supporting**
- Dashboard & Analytics
- System Settings & Audit Logs

## 5. OUT-OF-SCOPE (Strict Boundaries)
- No architectural refactoring.
- No Design System expansion or primitive creation.
- No component rewrites for aesthetic purposes.
- No API contract modifications.
- No database schema changes.
- No penetration testing or advanced security hardening.
- No CI/CD or deployment configuration.

## 6. DEFECT LIFECYCLE
Phase 09 strictly prohibits "fix while testing" behavior. Every issue must follow:
**DISCOVER → CLASSIFY → DOCUMENT → AUTHORIZE → FIX → RETEST**

Defects will be logged in `09.11_DEFECT_REGISTER.md` and classified as:
- DEFECT (Functional failure)
- REGRESSION (Worked previously, now broken)
- ACCEPTANCE FAILURE (Technical success, business failure)
- UX GAP (Sub-optimal flow)
- TECHNICAL DEBT (Architectural issue, not blocking)
- SCOPE FOLLOW-UP (Deferred to future phase)

## 7. EXIT CRITERIA (FINAL ACCEPTANCE GATE)
Phase 09 concludes ONLY when all 5 questions are definitively answered YES:
1. Does every required screen work?
2. Do critical business workflows complete successfully?
3. Do authorization boundaries work?
4. Do error/edge cases behave safely?
5. Did Phase 08 introduce any functional regression?
